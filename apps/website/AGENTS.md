# apps/website

## Purpose

The SvelteKit application — the dashboard product. One store per deployment, role-based dashboard staff, one Turso database, served by svelte-adapter-bun.

## Ownership

Owns routing, UI, server logic (oRPC handlers, Better Auth, Mistral OCR), local-disk file-storage wiring, and the adapter-bun service entry. The Drizzle schema and Turso/libSQL client factory live in `@repo/database`; `src/lib/server/db` wires dynamic runtime credentials into the web libSQL client.

## Local Contracts

- **One database**: the schema lives in `@repo/database` and merges Better Auth tables with the store domain. `src/lib/server/db/index.ts` reads `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN` from `$env/dynamic/private`, opens `@libsql/client/web`, calls `createDb`, and re-exports the schema and Drizzle operators. Database operations and transaction callbacks are async.
- **Foreign keys**: Turso enforces the schema's declared references and `onDelete` rules. Hard-delete handlers guard history before deleting. `order.customerId` is `ON DELETE SET NULL`, so deleting a customer preserves order snapshots.
- **Product removal is soft-delete**: `products.delete` sets `product.isArchived = true`; the row stays so order / inventory / purchase-invoice history keeps its FK target. Active-catalog reads (`products.list`, `products.checkout`, `products.stats`, `dashboard.stats`) filter `isArchived = false`; history reads (orders, inventory movements, `products.statsProduct` by id, `products.get`) still include archived products.
- **Add/edit management routes**: customers and suppliers use dedicated add/edit pages (`/customers/add`, `/customers/[id]/edit`, `/purchases/suppliers/add`, `/purchases/suppliers/[supplierId]/edit`) that mirror product add/edit pages. Add/edit navigation uses anchors styled with `buttonVariants`, not click handlers that call `goto` or open dialogs.
- **Primary sidebar**: Products (`/products`), Product Categories (`/products/categories`), Suppliers (`/purchases/suppliers`), and Purchased Invoices (`/purchases/invoices`) are top-level items alongside Customers, in that order; there are no separate Products or Purchases groups.
- **Dashboard page header**: `AdminDashboardHeader` renders the full-width 48px breadcrumb/action bar from inside the standard `p-4 md:p-6` route wrapper. Keep that wrapper full-width and constrain only content below the header. The component supplies a screen-reader-only `<h1>` from the final breadcrumb; pass `hasPageHeading` only when the page renders its own visible `<h1>`. The final breadcrumb must identify the current page.
- **Mobile card grids**: supplier, product, and product-category lists render one card per row while their main content container is narrower than 768px. Supplier and product-category grids then expand to two columns at 768px and three at 1024px; the compact product grid expands to four columns at 768px. Three-dot card/row action triggers are never hover-only. Product card action menus also sit outside the card-detail link so they work on touch screens.
- **Single store + roles**: the `shop` table has no `slug` and no `userId`; it is the one global shop row. `user.role` is `owner`, `admin`, `member`, or `user`. Dashboard access is `owner` / `admin` / `member`; `user` is reserved for future storefront/customer API accounts. **Owner-only sections**: `/settings` (Shop Settings: Profile / Business / Tax, plus `/settings/receipt`) and the **Team** group are restricted to `owner`. The sidebar hides both collapsible parents for non-owners; the routes guard with `settings/+layout.server.ts` and `team/+layout.server.ts` (non-owners redirect to `/`). The Profile and Business tabs persist independently through `orpc.shops.update`; omitted fields are preserved, so profile updates do not require or erase Business address/contact/**timezone** fields. The Business form uses a TanStack form-level Zod schema and shows localized inline errors plus invalid-field styling before submission. **Team** is a collapsible with two sub-items: **Management** (`/team` — invite-member via `orpc.invites.create` + reset-for-user via `orpc.recovery.forUser`) and **Members** (`/team/members` — read-only staff list of `owner`/`admin`/`member` accounts via `orpc.members.list`, columns: name, email, role, status, joined). Members is intentionally view-only for now; row actions (role edit, ban, remove) land as Team grows into employee management.
- **First-run gate**: `src/hooks.server.ts` exports `setupGate` (runs after Paraglide and before `authHandle`). It checks de-localized paths and emits localized redirects. With no users, it redirects everything to `/setup` except `/setup`, `/health`, static assets, first-owner auth endpoints (`sign-up/email`, `sign-in/email`, `sign-in/social`, OAuth callbacks, verify/session reads), and `/rpc/setup/*` (the setup create mutation). With users but no shop, `/setup` stays reachable (along with `/signin`, auth, and `/rpc/setup/*`) so an OAuth-created first owner can finish store setup. Once the shop exists, `/setup` and public email signup are closed.
- **Auth model**: better-auth `admin` plugin is enabled with `owner` as the only plugin admin role for now. The drizzle adapter is wired as `drizzleAdapter(db, { provider: "sqlite", schema })` with the bundled tables map from `@repo/database` — drizzle 1.x dropped `db._.fullSchema`, so without `schema` the adapter throws "Schema not found" at init; `admin` and `member` are dashboard staff roles without Better Auth user-management power until the invite hierarchy exists. `accountLinking.disableImplicitLinking: true` blocks email-match implicit linking. `/signup` is closed (redirects to `/signin`). `/signin` is email/password UI only, and `/accounts` does not expose provider linking or unlinking; already-linked Google accounts can still sign in via the Better Auth OAuth endpoint, while unlinked OAuth cannot create accounts after setup.
- **Link-first auth**: email delivery is not configured on the server yet, so `$lib/server/email.ts` currently logs and returns `false`; auth flows never depend on delivery. Verification, recovery, magic-link, and invite flows render copyable links. Two-factor authentication remains removed.
- **Copyable auth links**: `buildLinks` retains `{ offline, online }` field names for UI compatibility, but they now mean request-origin and configured `BETTER_AUTH_URL` and normally point to the same server instance.
- **Invite flow (owner-only, link-based)**: `orpc.invites.create` inserts a one-time 15-minute invite and returns copyable links for manual handoff. `/invite?token=` is the accept route (`+page.server.ts` validates + returns role); `orpc.invites.accept` **direct-inserts** `user` + credential `account` (role from the token, `emailVerified: true`, password hashed via `hashPassword` from `better-auth/crypto`) bypassing the user-create hook, consumes the invite, then signs in via `auth.api.signInEmail` (the `sveltekitCookies` after-hook applies the session cookie). This is the only dashboard-staff onboarding path; there is no email-based invite and no public signup.
- **Recovery flows**: `orpc.recovery.request` and `orpc.magicLink.request` mint Better Auth-compatible verification rows. `orpc.recovery.forUser` generates an owner-controlled reset link. `scripts/reset-password.ts` is the owner/admin lockout escape hatch and connects directly to Turso.
- **Routes**: `/verify-account`, `/forgot-password`, `/reset-password`, `/magic-link`, `/invite` live under the `(auth)` group (its `+layout.server.ts` `publicPrefixes` list allows them without a session; authed users are bounced to `/`). `/signup` stays closed. Dashboard routes live under `(dashboard)`.
- **Routing**: no store slug segment. Dashboard lives under the `(dashboard)` group at `/`, accounts at `/accounts`. Paraglide's URL strategy prefixes Myanmar routes with `/my` while English remains unprefixed; SvelteKit `reroute` de-localizes route matching. Internal links, `goto`, hard navigations, and redirects use `$lib/localize-path.ts` (`localizeHref`) so navigation preserves the active locale with root-relative paths in both SSR and CSR; the helper rejects external and protocol-relative redirect targets by falling back to `/` and returns SvelteKit's `ResolvedPathname` so ESLint recognizes the localized target as resolved. First-run routing is owned by `setupGate` in `hooks.server.ts` (see First-run gate above); dashboard/accounts layouts require a session with role `owner`, `admin`, or `member`. Routes use SvelteKit's default SSR + CSR rendering; do not enable prerendering globally.
- **No integrations feature**: the `/integrations` route, sidebar entry, social-connection oRPC handlers, and supporting UI are removed. Authentication supports Google OAuth only; Facebook OAuth is removed.
- **Store timezone** (`shop.timezone`, IANA name): DB stores UTC epochs; `/setup` defaults the timezone to the server runtime timezone and lets the user choose it; the store tz defines "today / this week / this month" and chart day-buckets. `orpc.setup.create` persists the selected timezone; the owner edits it later in Settings → Business. Dashboard KPI boundaries (`orpc.dashboard.stats`) and revenue-trend calendar days (`orpc.dashboard.revenueTrend`) use the shared `$lib/server/timezone.ts` helpers backed by `@internationalized/date` (DST-safe, no SQLite tz math); row bucketing uses `Intl.DateTimeFormat` in the store tz. `(dashboard)/+layout.server.ts` exposes `timezone` on `data` (rides the existing shop `findFirst`, no new query). The trend chart renders its server-bucketed date keys as UTC so labels match in every browser tz. Other pages (orders, invoices) still format in browser/server-local and adopt `data.timezone` as touched.
- **User language preference (URL-first, browser-local fallback)**: Paraglide catalogs support `en` and Myanmar Unicode `my`; strategy `["url", "preferredLanguage", "cookie", "baseLocale"]` uses `/my/...` for Myanmar and unprefixed routes for English. `/accounts` calls `setLocale`, which reloads onto the localized current URL; there is no DB write and no `orpc.user.updateLanguage`. `hooks.server.ts` runs `handleParaglide` before route guards, forwards its de-localized request, and exposes the resolved locale as `locals.language` (used to seed the `/accounts` dropdown). The cookie remains a per-browser fallback and does not follow the account to another device; invalid/missing preference falls back to English after URL and browser-language detection. UI copy, validation, statuses, accessibility labels, and shared primitive labels localize; user/OCR data, English date/number/currency formatting, auth emails, and receipt/invoice document content remain unchanged. Myanmar glyphs use the bundled offline Noto Sans Myanmar subset under `static/fonts`.
- **Localized API errors**: user-facing oRPC failures return `data: { key, values? }` rather than localized backend messages. `$lib/error-message.ts` resolves those keys through Paraglide, maps known Better Auth codes, and hides unknown/raw errors behind localized `something_went_wrong`; server logs retain raw details. Input/output validation failures are normalized at `/rpc/[...rest]`.
- **POS flow**: `/cart` (Point of Sale — build the cart via barcode scan or product search) → `/checkout` (review, attach a customer, place the order) → `/orders/[id]`. The cart and product-form scanner viewports use `h-36`; the camera video crops to that viewport and the internal barcode frame scales within it. Camera barcode scanning (`BarcodeScanner.svelte`, also used by `ProductForm.svelte`) relies on the browser's HTTPS secure-context requirement. It suppresses continuous duplicate frames while accepting the same barcode again after it has left the camera view. Cart state is shared client-side via `src/lib/cart.svelte.ts`, a Svelte 5 reactive class backed by runed `PersistedState` (`localStorage`, key `stores4u:cart`) — a refresh keeps the cart; SSR-safe (server singleton stays empty). The customer is optional: walk-in (default, anonymous) or an existing/new customer attached as `customerId` (the `checkout` handler snapshots `customer_name`/`customer_phone` onto the order). `/checkout` has a client-side empty-cart guard that bounces back to `/cart`. The sidebar/CTA entry point is `Point of Sale` → `/cart`. **Receipt**: shared renderer `src/lib/components/receipt/Receipt.svelte` takes `data` (shop + order fields) + `config` (`ReceiptConfig`) + `currency` props and renders the paid POS receipt (58/80mm, monospace). It has two consumers: (1) `/settings/receipt` under the collapsible **Settings** sidebar parent (children: `Shop` → `/settings`, `Receipt` → `/settings/receipt`) renders a config Card (paper width, show logo/address/state/country/phone/email, footer text) wired to `orpc.receipt.get` / `orpc.receipt.update` (persisted in the `receipt_settings` singleton table) plus a live preview using the real shop header and representative order data (`ReceiptSettingsForm.svelte` owns the editable draft); (2) the order-detail `Receipt` button on `/orders/[id]` opens a read-only dialog with real order data (`orpc.orders.get`, including `vatCents`) and the saved config. The receipt header uses the canonical shop name plus its description when present; address, state, country, and phone remain independently controlled by receipt settings. Postal code is never rendered. Settings preview, order preview, PNG export, and print all use the same renderer. Successful checkout navigates to `/orders/[id]?print=receipt`; the order page consumes that one-shot signal, removes it from history, opens the receipt, waits for fonts/images, and invokes the browser/OS print dialog once on all devices. Print completion or cancellation leaves the receipt dialog open. Manual print and 3× PNG native share (browser-download fallback) remain available; automatic Gallery saving, silent printing, direct Web Bluetooth protocols, and PDF export remain deferred. Supplier documents remain Purchase Invoices.
- **Setup is load + oRPC**: `/setup` has a `+page.server.ts` `load` returning `{ needsAccount, defaultTimezone }` (whether the first owner still needs creating plus the server runtime timezone) for form rendering, and `orpc.setup.create` (mutation) creates the first owner via `auth.api.signUpEmail` when needed and inserts the one shop row. The page uses tanstack/svelte-form + tanstack-query; the client `goto`s `/signin?setup=1` (owner just created) or `/` (owner already signed in). Reachability is owned by `setupGate` (see First-run gate); the handler is the auth/role trust boundary.
- **Mutation cache coherence**: successful client mutations invalidate every affected TanStack oRPC router key (`orpc.<router>.key()`), including cross-domain detail, aggregate, and infinite-query caches; mutations of SvelteKit-loaded data also use `invalidateAll`. Redirect-only auth/setup and staging uploads need no query invalidation when no cached query reads their writes.
- **oRPC**: `src/lib/server/orpc/base.ts` defines `authMiddleware`, `ownerMiddleware`, and `shopMiddleware` / `protectedShopMiddleware` (resolve the single store, no input). `protectedShopMiddleware` requires a dashboard role and the single shop row; store, tax, and receipt-setting mutations instead run `ownerMiddleware` before `shopMiddleware`. Product/category reads are internal dashboard APIs (no storefront-safe catalog API exists), and product/category list page sizes cap at 100. `setupCreateHandler` (`orpc.setup.create`) additionally enforces a global shop-count guard (one shop per deployment) and is the only shop-creation mutation. Handlers import the single `db` directly from `$lib/server/db`; there is no per-request db middleware.
- **Invoice OCR (Mistral, single call)**: `src/lib/server/ocr/mistral-invoice.ts` runs one `@mistralai/mistralai` `ocr.process` call with `documentAnnotationFormat: json_schema` to return structured `ExtractedInvoiceData` directly — no separate verification/chat step, no second call. Called from `orpc.purchaseInvoices.processFile` during the invoice review workflow. PDFs and images are sent inline as base64 data URLs, avoiding a remote Mistral Files cleanup lifecycle. No local preprocessing (`pdftoppm` is gone). The uploaded-file buffer is passed to Mistral as-is; the user is responsible for uploading a correct invoice (no "is-it-an-invoice" gate). The old Mastra/OpenRouter Gemini extraction+verification agents and `_lib/image-utils.ts` are removed, and the `@mastra/*`, `mastra`, and `@openrouter/sdk` deps are uninstalled. `MISTRAL_API_KEY` is read from SvelteKit's `$env/dynamic/private`, forwarded through Turbo's root `globalEnv`, and only required at process time (missing key never blocks build/dev). Vite's `envDir` points to the monorepo root so direct `apps/website` commands load the same root `.env` as Turbo commands.
- **Invoice quick product creation**: invoice review and edit share `ItemsCard.svelte`. The quick-create form prefills Retail Price from the item's current, user-correctable unit cost; a zero cost leaves it empty, while a non-blocking warning remains until Retail Price is above that cost.
- **File storage**: `src/lib/server/storage.ts` persists objects under `STORAGE_DIR` (`$env/dynamic/private`, falling back to gitignored `apps/website/.storage` in dev) and serves them through `/storage/[...key]`. Every disk operation validates keys first; keys are slug-free (`images/...`, `invoice-files/...`, `avatars/...`) and reject empty/traversal segments. Invoice uploads trust JPEG/PNG/PDF magic bytes and canonicalize extensions. Image/avatar uploads reject SVG and retain accepted JPEG/PNG/WebP bytes as-is (no image reprocessing today). Responses derive MIME from canonical keys and set CSP, CORP, and anti-sniffing headers; unknown extensions download as attachments. Stored files have no replication or offsite backup — operators own disk backups.

## Work Guidance

- ESLint checks authored `src/**/*.svelte` files without TypeScript project service; Biome handles repository-wide TypeScript/JavaScript linting.
- Run root `bun run setup` once on a new development machine. It authenticates the Turso CLI when needed, provisions isolated Turso development resources, writes generated database/auth credentials to root `.env`, prepares the local upload-storage directory, and applies committed migrations. Later `bun run dev` calls only Vite and must not provision resources or migrate. Ignored root `.env.prod` supplies production build, migration, and service values; do not copy production credentials into `.env`.
- Commit generated `packages/database/drizzle/` migrations. Root `bun run deploy` validates `.env.prod`, builds, then applies committed migrations to Turso; delivering built code to the Lightsail VM and restarting its service is operator work until a VM bootstrap script exists. Do not migrate during app startup or `bun run dev`.
- Password reset: `RESET_EMAIL=... RESET_PASSWORD=... bun run scripts/reset-password.ts` updates an owner/admin credential directly in Turso.

## Verification

- `bun run test` (Vitest unit tests)
- `bun run typecheck` (svelte-check, 0 errors expected)
- `bun run dev` then smoke routes: `/`, `/setup`, `/signin`, `/health`

- `src/lib/server/ocr` — Mistral OCR invoice extraction (`mistral-invoice.ts`), used by the purchase-invoice workflow.
