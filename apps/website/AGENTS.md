# apps/website

## Purpose

The SvelteKit application — the dashboard product. Single-store-per-server: one store, role-based dashboard staff, one SQLite database.

## Ownership

Owns: routing, UI, server logic (oRPC handlers, better-auth, mastra agents). The Drizzle schema and SQLite client factory live in `@repo/database` (`packages/database`); `src/lib/server/db` is a thin env-wiring shim that opens the `bun:sqlite` client from `DATABASE_PATH`, calls `createDb`, and re-exports everything from `@repo/database`.

## Local Contracts

- **One database**: the schema lives in `@repo/database` (`packages/database/src/schema`), which merges better-auth tables (`auth.ts`, `shop-info.ts`) with the store domain (`product`, `order`, `supplier`, `customer`, `inventory`, `purchaseInvoice`, `tax`, `image`) and one merged `relations.ts`. `src/lib/server/db/index.ts` is the env-wiring shim: it reads `DATABASE_PATH` from `$env/static/private`, opens the `bun:sqlite` client, and calls `createDb`; it re-exports `drizzle-orm` operators and the full schema from `@repo/database`. Handlers keep importing tables, operators, and `db` from `$lib/server/db` (the shim) or directly from `@repo/database`.
- **Foreign keys are enforced**: `createDb` runs `PRAGMA foreign_keys = ON`, so the schema's `references()` + `onDelete` rules fire. Hard-delete handlers must guard history before deleting (see `delete_supplier`, `delete_category`, `delete_invoice_file`); a `references()` with no `onDelete` blocks the delete at the DB when child rows exist. Exception: `customers.delete` needs no guard — `order.customerId` is `ON DELETE SET NULL`, so deleting a customer orphans order links while the order's snapshot columns (`customer_name`/`customer_phone`) keep historical invoices intact.
- **Product removal is soft-delete**: `products.delete` sets `product.isArchived = true`; the row stays so order / inventory / purchase-invoice history keeps its FK target. Active-catalog reads (`products.list`, `products.checkout`, `products.stats`, `dashboard.stats`) filter `isArchived = false`; history reads (orders, inventory movements, `products.statsProduct` by id, `products.get`) still include archived products.
- **Add/edit management routes**: customers and suppliers use dedicated add/edit pages (`/customers/add`, `/customers/[id]/edit`, `/purchases/suppliers/add`, `/purchases/suppliers/[supplierId]/edit`) that mirror product add/edit pages. Add/edit navigation uses anchors styled with `buttonVariants`, not click handlers that call `goto` or open dialogs.
- **Primary sidebar**: Products (`/products`), Product Categories (`/products/categories`), Purchase Invoices (`/purchases/invoices`), and Suppliers (`/purchases/suppliers`) are top-level items alongside Customers; there are no separate Products or Purchases groups.
- **Single store + roles**: the `shop` table has no `slug` and no `userId`; it is the one global shop row. `user.role` is `owner`, `admin`, `member`, or `user`. Dashboard access is `owner` / `admin` / `member`; `user` is reserved for future storefront/customer API accounts. **Owner-only sections**: `/settings` (Shop Settings: Profile / Business / Tax, plus `/settings/invoice`) and the **Team** group are restricted to `owner`. The sidebar hides both collapsible parents for non-owners; the routes guard with `settings/+layout.server.ts` and `team/+layout.server.ts` (non-owners redirect to `/`). **Team** is a collapsible with two sub-items: **Management** (`/team` — invite-member via `orpc.invites.create` + reset-for-user via `orpc.recovery.forUser`) and **Members** (`/team/members` — read-only staff list of `owner`/`admin`/`member` accounts via `orpc.members.list`, columns: name, email, role, status, joined). Members is intentionally view-only for now; row actions (role edit, ban, remove) land as Team grows into employee management.
- **First-run gate**: `src/hooks.server.ts` exports `setupGate` (runs before `authHandle`). With no users, it redirects everything to `/setup` except `/setup`, `/health`, static assets, first-owner auth endpoints (`sign-up/email`, `sign-in/email`, `sign-in/social`, OAuth callbacks, verify/session reads), and `/rpc/setup/*` (the setup create mutation). With users but no shop, `/setup` stays reachable (along with `/signin`, auth, and `/rpc/setup/*`) so an OAuth-created first owner can finish store setup. Once the shop exists, `/setup` and public email signup are closed.
- **Auth model**: better-auth `admin` plugin is enabled with `owner` as the only plugin admin role for now. The drizzle adapter is wired as `drizzleAdapter(db, { provider: "sqlite", schema })` with the bundled tables map from `@repo/database` — drizzle 1.x dropped `db._.fullSchema`, so without `schema` the adapter throws "Schema not found" at init; `admin` and `member` are dashboard staff roles without Better Auth user-management power until the invite hierarchy exists. `accountLinking.disableImplicitLinking: true` blocks email-match implicit linking. `/signup` is closed (redirects to `/signin`). `/signin` is email/password UI only, and `/accounts` does not expose provider linking or unlinking; already-linked Google/Facebook accounts can still sign in via the Better Auth OAuth endpoint, while unlinked OAuth cannot create accounts after setup.
- **Online-capable auth, graceful offline**: the app is deployed assuming the internet is up, but must keep working when it blips. SMTP is generic (`SMTP_HOST/PORT/SECURE/USER/PASSWORD/FROM`, optional — read via `$env/dynamic/private` so a missing var never breaks the build/dev) and wired through `$lib/server/email.ts` (`sendEmail` / `sendAuthEmail`), which **never throws** (try/catch + log + return false). Email verification (`requireEmailVerification: true`, `sendOnSignUp: false`; `sendVerificationEmail`) and magic-link (`magicLink` plugin, `disableSignUp: true` — `sendMagicLink` is wired but never hit, since `orpc.magicLink.request` mints the token itself) callbacks all call `sendAuthEmail` and never throw. Forgot-password has **no** better-auth callback: `orpc.recovery.request` mints the reset token and calls `sendAuthEmail` directly (better-auth's `/forget-password` endpoint is never hit). Two-factor authentication is removed at this time (no `twoFactor` plugin, no client plugin, no `/accounts` UI); the `two_factor` table + `user.two_factor_enabled` column remain in the schema as orphaned no-ops pending a drop migration if 2FA stays gone.
- **Links are primary, email is convenience**: every email-auth flow (invite, forgot-password, magic-link, owner reset-for-user) generates a **two-link pair** via `$lib/server/links.ts` `buildLinks(token, path, requestOrigin)` → `{ offline, online }`. Offline uses the request origin (reachable on LAN / same wifi); online uses `BETTER_AUTH_URL`. The pair is always surfaced on screen (copyable); email is attempted best-effort and failure just means "copy a link below." This is the unstable-internet fallback. On-screen link display for forgot-password/magic-link is insecure-by-design on a trusted store LAN (accepted per Q9-B).
- **Invite flow (owner-only, link-based)**: `orpc.invites.create` (owner middleware) inserts a row in the `invite` table (`role`, `createdById`, 15-min `expiresAt`, `consumedAt`, `consumedById`) and returns the offline+online link pair; the owner copies whichever fits (SMS/voice when the internet is down). `/invite?token=` is the accept route (`+page.server.ts` validates + returns role); `orpc.invites.accept` **direct-inserts** `user` + credential `account` (role from the token, `emailVerified: true`, password hashed via `hashPassword` from `better-auth/crypto`) bypassing the user-create hook, consumes the invite, then signs in via `auth.api.signInEmail` (the `sveltekitCookies` after-hook applies the session cookie). This is the only dashboard-staff onboarding path; there is no email-based invite and no public signup.
- **Recovery flows**: `orpc.recovery.request` (public, `/forgot-password`) and `orpc.magicLink.request` (`/magic-link`) mint a token directly into better-auth's `verification` table in the exact shape its endpoints expect (`reset-password:<token>`→userId, and `<token>`→`JSON{email,name}`) so `/reset-password?token=` POSTs to `/api/auth/reset-password` and the magic-link pair points straight at `/api/auth/magic-link/verify`. `orpc.recovery.forUser` (owner, email-based, at `/team`) generates a reset-link pair with no email. `scripts/reset-password.ts` stays as the offline owner/admin lockout escape hatch (same `hashPassword`). There is no self-service same-LAN reset-link generation for a signed-in user; a signed-in user changes their password via the `/accounts` Security form, and a locked-out user uses the email-based `/forgot-password`.
- **Routes**: `/verify-account`, `/forgot-password`, `/reset-password`, `/magic-link`, `/invite` live under the `(auth)` group (its `+layout.server.ts` `publicPrefixes` list allows them without a session; authed users are bounced to `/`). `/signup` stays closed. Dashboard routes live under `(dashboard)`.
- **Routing**: no slug segment. Dashboard lives under the `(dashboard)` group at `/`, accounts at `/accounts`. First-run routing is owned by `setupGate` in `hooks.server.ts` (see First-run gate above); dashboard/accounts layouts require a session with role `owner`, `admin`, or `member`.
- **No integrations feature**: the `/integrations` route, sidebar entry, social-connection oRPC handlers, and supporting UI are removed. Facebook OAuth remains part of authentication.
- **POS flow**: `/cart` (Point of Sale — build the cart via barcode scan or product search) → `/checkout` (review, attach a customer, place the order) → `/orders/[id]`. Cart state is shared client-side via `src/lib/cart.svelte.ts`, a Svelte 5 reactive class backed by runed `PersistedState` (`localStorage`, key `stores4u:cart`) — a refresh keeps the cart; SSR-safe (server singleton stays empty). The customer is optional: walk-in (default, anonymous) or an existing/new customer attached as `customerId` (the `checkout` handler snapshots `customer_name`/`customer_phone` onto the order). `/checkout` has a client-side empty-cart guard that bounces back to `/cart`. The sidebar/CTA entry point is `Point of Sale` → `/cart`. **Invoice**: shared renderer `src/lib/components/invoice/Invoice.svelte` takes `data` (shop + order fields) + `config` (`InvoiceConfig`) + `currency` props and renders a thermal-style receipt (58/80mm, monospace). It has two consumers: (1) `/settings/invoice` — a real route under the collapsible **Settings** sidebar parent (children: `Shop` → `/settings`, `Invoice` → `/settings/invoice`) that renders a config Card (paper width, show logo/address/phone/email, footer text) wired to `orpc.invoice.get` / `orpc.invoice.update` (persisted in the `invoice_settings` singleton table) plus a **live preview using hardcoded static data** (`PREVIEW_DATA` in the `InvoiceSettingsForm.svelte` child that owns the editable draft); (2) the order-detail `Invoice` button on `/orders/[id]`, which opens a read-only `@repo/ui/dialog` rendering the same component with **real order data** (`orpc.orders.get`, which returns `vatCents`) and the saved config. The old debug-only `/orders/[id]/invoice` route and `settings/Receipt.svelte` are removed. Thermal printing itself remains deferred — this is on-screen preview only.
- **Setup is load + oRPC**: `/setup` has a `+page.server.ts` `load` returning `{ needsAccount }` (whether the first owner still needs creating) for form rendering, and `orpc.setup.create` (mutation) creates the first owner via `auth.api.signUpEmail` when needed and inserts the one shop row. The page uses tanstack/svelte-form + tanstack-query; the client `goto`s `/signin?setup=1` (owner just created) or `/` (owner already signed in). Reachability is owned by `setupGate` (see First-run gate); the handler is the auth/role trust boundary.
- **oRPC**: `src/lib/server/orpc/base.ts` defines `authMiddleware` and `shopMiddleware` / `protectedShopMiddleware` (resolve the single store, no input). `protectedShopMiddleware` requires a dashboard role and the single shop row. `setupCreateHandler` (`orpc.setup.create`) additionally enforces a global shop-count guard (one shop per server) and is the only shop-creation mutation. Handlers import the single `db` directly from `$lib/server/db`; there is no per-request db middleware.
- **Invoice AI (no chat)**: `src/lib/server/mastra` holds only the invoice extraction/verification agents and `_lib/image-utils.ts`, called from `orpc.purchaseInvoices.processFile` during the invoice review workflow. The conversational shop-assistant chat (`/chats`, `/api/ai/shop-assistant`, mastra registry, store memory, and the `threads` oRPC router) has been removed.
- **File storage** (driver-selected by `STORAGE_DRIVER` in `src/lib/server/storage.ts`): `local` writes to `STORAGE_LOCAL_DIR` and serves via the public `/storage/[...key]` route (no signing; offline-capable); any other value uses S3/R2 via Bun's `S3Client` with presigned downloads. Keys are slug-free (`images/...`, `invoice-files/...`, `avatars/...`). Stored URLs are driver-specific — `/storage/<key>` for local, `${STORAGE_PUBLIC_URL}/<key>` for S3 — and reversible via `extractObjectKey`. Path traversal is blocked by the shared `safeJoinPath` helper (unit-tested).

## Work Guidance

- `DATABASE_PATH` must be set (see `.env.example`). Run `bun run db:migrate` to create/sync the schema into the SQLite file.
- Drizzle migrations (`drizzle/`) are gitignored; use `db:generate` + `db:migrate` .
- Offline password reset: `RESET_EMAIL=... RESET_PASSWORD=... bun run scripts/reset-password.ts` resets an owner/admin password directly against `DATABASE_PATH` (lockout escape hatch; bypasses the session-gated admin API; both email + password read from env so neither hits argv / shell history). Owner/admin roles only; refuses member/user.

## Verification

- `bun run test` (Vitest unit tests)
- `bun run typecheck` (svelte-check, 0 errors expected)
- `bun run dev` then smoke routes: `/`, `/setup`, `/signin`, `/health`
